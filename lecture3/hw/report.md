# 项目理解报告

请尽量使用自己的语言回答以下问题。可以引用少量关键代码或伪代码，但不要只粘贴实现。
完成一节后删除该节末尾的待填写标记；本地检查会拒绝仍有未完成章节的报告。

## 1. 图像生命周期与所有权

`ImageSequenceSource` 里只有一个 `buffer_`，每读一张新图都会把像素写进这块内存。
这和相机 SDK 重复使用采集缓冲区的情况很像。`cv::Mat` 普通赋值只复制图像头和增加
引用计数，两个 `Mat` 仍然指向同一块像素内存。因此原来的 `frame.image = buffer_`
会让已经入队的旧帧随后续采集一起变化。

我在帧越过数据源边界时使用 `buffer_.clone()`。`clone()` 为当前像素分配独立存储，
所以每个 `Frame` 持有自己的图像数据。`Frame` 在队列中移动时，`cv::Mat` 的引用计数
会保证这块数据一直存活，而下一次 `next()` 只会覆盖数据源自己的 `buffer_`。

## 2. 并发处理与恰好一次

producer 每产生一帧只调用一次 `push`。多个 worker 都在同一个队列上调用 `pop`，
但 `pop` 会在队列的互斥锁保护下取出队首并立即将它删除。这保证一个队列元素
只能被一个 worker 拿到，因而不会重复处理。只要 `push` 成功，该帧就会留在队列里
直到某个 worker 取走，因此也不会漏掉已经入队的帧。

输入耗尽后 producer 调用 `close()`。它会唤醒所有等待的 worker，但不会清空队列。
队列里已有的帧仍会继续被取出处理。正在处理的 worker 先完成当前帧，然后再次
调用 `pop`。只有当队列同时处于“已关闭且已空”状态时，`pop` 才返回 `false`，worker
才退出循环。

## 3. 共享统计数据

producer 会写 `produced_`，多个 worker 会写 `processed_`、`saved_` 和 `corrupted_`，
主线程在等待结束后读取快照。原来的增量操作是“读取旧值、计算、写回”三步，
多个线程可能读到相同的旧值并相互覆盖结果，而且这种未同步的读写在 C++ 中属于
数据竞争。

我用同一个 `mutex_` 保护四个计数器。每个更新函数都在持有锁时完成整个增量操作，
所以不会丢失更新。`snapshot()` 也在同一把锁下一次读取全部四个字段，得到的是
同一时刻的一致视图，不会拼出一个一部分是旧值、一部分是新值的快照。

## 4. 线程关闭协议

显式等待时，`start()` 先启动 worker，再启动 producer。producer 读完输入后关闭队列，
各 worker 将队列排空后退出。`wait()` 先 `join` producer，此时可以确定不再有新帧入队，
也可以确定队列已关闭；然后它逐个 `join` worker。因为关闭会唤醒等待者，worker
不会永久卡在 `pop`上。`wait()` 返回后没有任何后台线程再访问 `Pipeline` 成员。

不显式等待时，析构函数会直接调用同一个 `wait()`，因此事件顺序和上面相同。
在成员被销毁前，所有线程都已经被回收，所以不会析构可 `join` 的 `std::thread`
而触发 `std::terminate`，也不会留下对队列、数据源或统计对象的悬空访问。

`wait()` 可以重复调用，因为它只对 `joinable()` 的线程执行 `join`，已经回收的线程会被跳过。
`start()` 则只允许调用一次；第二次调用会抛出 `std::logic_error`，避免在已关闭、无法重开的
队列上再启动一套线程。如果创建线程的过程中出现异常，`start()` 会关闭队列并回收已启动的线程
后再抛出，不会留下半启动状态的可运行线程。
